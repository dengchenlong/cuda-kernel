# Handoff: 攻克 cuda-kernel hist 4K 两项边缘项（跑赢 OpenCV-CUDA）

> 目标会话：在服务器（RTX 5090 D v2, sm_120, CUDA 12.8）上让 `hist-gray 3840x2160` 与
> `hist-binary 3840x2160` 两项 benchmark 跑赢 OpenCV-CUDA 4.14。
> 项目：`~/cuda-kernel`（GitHub dengchenlong/cuda-kernel），当前 main = `6d15241`。

## 背景（勿重复调查，结论都在归档里）

本项目是高性能 CUDA 图像算子库，对标 OpenCV-CUDA。当前 benchmark 120 项中 118 项稳定 WIN，
唯一未达标的就是这两个 4K hist 项：

| 项 | 服务器三轮实测 | cv 快路径 |
|---|---|---|
| hist-binary 3840x2160 | mine 0.010ms | 0.009ms（0.90x） |
| hist-gray 3840x2160 | mine 0.014ms | 0.010ms（0.71x） |

**已证伪的方向（不要再走回头路）**，详见 `spikes/003-hist-arch/README.md`：
1. `__match_any_sync` warp-aggregated：随机 8-bit 数据 32 lane 碰撞期望仅 ~2 组，match 开销
   大于聚合收益，慢 3-7x（0.0152/0.0497ms）。
2. per-lane 私有 u16 计数 + 归约：64KB smem/块压死 occupancy（每 SM 2 块），慢 1.3-2.7x
   （0.0090/0.0191ms）。
3. grid 大小已调优：`clamp((H+7)/8, 48, min(256, max(48, smCount)))`，4K=170blk 实测最优
   （256blk 反而 0.0109ms vs 170blk 0.0092ms）。
4. 每线程多 uint4（2u4/4u4）：无一致收益。

**已知的踩坑（照做，别再踩）**：
- `__match_any_sync(0xffffffff, ...)` 在 warp 部分活跃（行尾 cols4%32≠0）时死锁，必须用
  `__activemask()`（NVIDIA warp-aggregated atomic 官方写法）。
- OpenCV cudafilters 计时**状态敏感**：同一 kernel 双峰 0.03/0.28ms。探针计时必须
  统一预热 + 交错计时 + 取中位数；cv 对照要用独立输出 GpuMat（calcHist 输出复用 integral
  的 (W+1)x(H+1) 8MB buffer 会卡死分配器）。
- `k=31` gaussian 会让 OpenCV 4.14 自己崩（invalid argument），与本项目无关但别惊讶。

## 现版实现（要被打败的基线）

`src/histogram.cu`：fast path = 32x8 block（threadIdx.y*32+threadIdx.x），uint4 向量化读，
每字节 `atomicAdd(&shist[bin], 1)` 打 per-block smem 直方图（256 int），行 grid-stride；
块结束后写 partials[blockIdx.x*256 + tid]，`__threadfence()` + atomicInc last-block 归约，
最后一个 block 汇总并完全覆写 d_hist（无需预清零，这是之前省掉 20μs memset 的优化）。
binary 版：popcount 数 0/255，grid 固定 256。

## cv 侧情报（逆向起点）

OpenCV 4.14 `modules/cudaimgproc/src/histogram.cu`（本机源码：
`~/vcpkg/buildtrees/opencv4/src/4.14.0-*.clean/modules/cudaimgproc/src/histogram.cu`）。
值得先读它找出 4K gray 路径快的真实原因再动手。已观察到的现象：
- cv calcHist 在 1080p/720p 输给我们（我们 1.03-1.38x），只在 4K 反超 —— 说明不是算法
  结构性优势，更可能是 4K 时它某种 block/smem 配置恰好更好，或我们的 170blk 在 4K 有
  尾延迟/atomic 冲突放大。
- hist-binary 4K 只差 10%（0.010 vs 0.009），是最容易先攻破的一项；binary 版我们用
  popcount，cv 4K 快路径 0.009ms ≈ 921 GB/s 有效读带宽（8.29MB / 9μs），接近该卡
  实测带宽上限 —— 先用 bandwidthTest 类 micro-benchmark 确认 8.29MB 随机读的物理上限，
  判断剩余空间是算法还是带宽墙。

## 建议的攻坚方向（按优先级）

1. **读 cv 源码**（半小时）：找到 cv 4.14 calcHist 的 4K 路径参数（block 数、每线程
   处理量、smem 布局、是否用 __ldg/texture、last-block 还是两 kernel 归约）。
2. **micro-benchmark 物理上限**：8.29MB uint4 只读不给 atomic 的 kernel 能跑多快？
   如果 0.009ms 就是墙，binary 项目标改为 0.0085ms 才有意义；如果纯读 0.005ms，
   空间在 atomic 冲突。
3. **smem atomic 冲突分析**：现版 shist[256] 单副本，warp 内随机 bin 的 bank 冲突 +
   atomic 串行化是主要嫌疑。可试：32 副本 smem 直方图（每 lane 按跳变 hash 选副本，
   参考 NVIDIA histogram256 SDK sample 的 tag 方案）、或 warp 内先排序/聚合再 atomic。
4. **每线程聚合**：lane 私有寄存器累计若干字节后再一次性 atomicAdd（v2 证伪的是
   256-bin 全私有，寄存器只能放 4-8 个 bin，需要按数据分布动态选 top-bin —— 谨慎，
   可能不值）。
5. 每改一版：先小探针（spikes/003-hist-arch/ 下加 probe5.cu，主口径交错计时），
   赢了再进 src/，跑 smoke（hist max diff 必须为 0）+ benchmark 3 轮。
6. 笔记本 sm_61 兼容：不要用 sm_61 没有的指令；grid 公式里 48 下限必须保留（1050 Ti
   6 SM 曾因 clamp 写错回归过）。改完后需要笔记本复验（交接给用户转笔记本 Hermes）。

## 工程环境（服务器）

- 仓库 `~/cuda-kernel`，main = 6d15241；新工作开分支 `spike-hist4k`（勿直接改 main）。
- vcpkg OpenCV-CUDA 4.14 已装：`~/cuda-kernel/vcpkg_installed/x64-linux/`
  （include/opencv4、lib、静态库 libopencv_core4.a 等）。改动算子后重编项目：
  `export PATH=$HOME/.local/bin:/usr/local/cuda/bin:$PATH; cd ~/cuda-kernel &&
   cmake --build build-vcpkg -j 8`，产物 `build-vcpkg/smoke`、`build-vcpkg/benchmark`。
- 单文件探针编译模板（在 spikes/003-hist-arch/ 下沿用）：
  `nvcc -O3 -arch=native -std=c++17 -I$HOME/cuda-kernel/vcpkg_installed/x64-linux/include/opencv4
   -L$HOME/cuda-kernel/vcpkg_installed/x64-linux/lib
   -Xlinker "-rpath,$HOME/cuda-kernel/vcpkg_installed/x64-linux/lib"
   probeN.cu -o pNrun -lopencv_core4 -lopencv_cudaarithm4 -lopencv_cudaimgproc4
   -lopencv_cudafilters4 -lopencv_imgproc4
   -lnppc -lnppif -lnppig -lnppist -lnppial -lnppidei -lnppicc -lnppim -lnppisu -lnppitc -lnpps -lz -lcudart`
- benchmark 对 cv 计时必须交错 + 多轮取最快（cv 状态敏感），否则会测出假 WIN/假 lose。
- push 无需交互（凭据已配好）：`git push origin <branch>`。GitHub Actions CI 在 main 上
  跑 Windows 构建，合并前保持 smoke/benchmark 本地全绿即可。
